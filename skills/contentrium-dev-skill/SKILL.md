# Contentrium Dev Skill

독립 실행형 데스크톱 앱에는 개발·설치·배포 기준을 적용한다. 스킬·플러그인에는 소개·설치 안내·승인된 배포·릴리스 관리와 관련 보안 기준만 적용하며, 개발 방식과 패키징은 해당 플랫폼을 유지한다. 사용자의 명시적 요구와 기존 프로젝트 구조를 우선하며, 이 스킬을 추가 작업의 승인으로 사용하지 않는다.

## 에이전트 호환성

표준 `SKILL.md`를 읽을 수 있는 에이전트에서 사용한다. 참고자료는 이 파일의 디렉터리를 기준으로 상대 경로로 읽는다. `agents/openai.yaml`은 Codex용 선택 메타데이터이며 다른 에이전트는 무시해도 된다.

GitHub·브라우저·이미지 생성 기능은 현재 에이전트에 제공된 도구를 사용한다. 사용자 또는 프로젝트의 도구 제한이 우선한다. 특정 플러그인이나 Aside가 없는 환경에 설치·인증을 임의로 강제하지 않는다. 도구 선택은 [배포](references/deployment.md)의 환경별 기준을 따른다.

Mac에 이 스킬 자체를 설치하거나 설치 방법을 안내할 때는 [Mac 스킬 설치 안내](references/mac-skill-install.md)를 읽는다. 앱 제작 시 매번 읽을 필요는 없다.

## 작업 범위 선택

| 요청 | 적용 범위 |
| --- | --- |
| 새 데스크톱 앱 제작 | 아래 신규 앱 기준과 설치 참고 문서 |
| 기존 앱의 기능·오류 수정 | 기존 구조를 유지하고 변경 및 영향 범위만 검증 |
| 설치기 제작·수정 | 설치 참고 문서의 해당 항목 |
| 데스크톱 앱·스킬·플러그인의 GitHub 소개·README·배포·릴리스 | 배포 참고 문서의 공통 항목과 해당 유형의 항목만 적용 |
| 스킬·플러그인의 기능·구조 수정 | 해당 플랫폼 기준을 따르고 데스크톱 개발 기준은 적용하지 않음 |
| 그 외 MCP·CLI·스크립트·웹사이트·웹앱 작업 | 명시적으로 요청한 공통 소개·배포 기준만 적용 가능하며 기존 유형 유지 |

- ‘프로그램’이라는 표현만으로 데스크톱 앱으로 판단하지 않는다. 기존 자료와 실행 환경을 확인하고, 유형에 따라 결과가 크게 달라지는데 판단할 근거가 없을 때만 질문한다.
- 복합 프로젝트에서 데스크톱 개발·설치·화면 기준은 데스크톱 구성요소에만 적용한다. 기존 플러그인·스킬 등을 별도 앱으로 감싸지 않는다.
- 기존 앱의 작은 수정에 신규 설치기, 트레이, 자동 업데이트 또는 저장소 개편을 추가하지 않는다.
- 개발·수정·테스트 요청만으로 공개 저장소를 생성하거나 배포하지 않는다. 배포 요청이 있으면 승인된 범위 안에서 진행하며 재승인을 반복하지 않는다.

## 신규 데스크톱 앱 공통 기준

- 대상 OS는 사용자의 요구와 기존 프로젝트 자료에서 먼저 확인한다. 아무 근거도 없을 때만 Windows 설치형을 기본으로 하며, 에이전트가 실행되는 OS만으로 대상 OS를 결정하지 않는다. 다중 OS 지원은 요청된 범위에만 적용한다.
- 새 독립 실행형 데스크톱 앱의 핵심 로직·파일 처리·시스템 연동은 Rust를 기본으로 개발한다. UI 기술은 요구사항과 대상 환경에 맞게 선택하며 Rust와 연동할 수 있다. UI까지 Rust로 강제하거나 특정 UI 프레임워크를 고정하지 않는다.
- 기존 앱의 수정·기능 추가·모듈 추가는 기존 스택을 따르며 Rust 전환을 강제하지 않는다. 스킬·플러그인·MCP·CLI·스크립트·웹사이트·웹앱에는 이 언어 기준을 적용하지 않는다. 복합 프로젝트에서도 별도 제작을 요청받은 새 독립 실행형 데스크톱 앱에만 적용하며, 기존 앱에 추가하는 구성요소에는 소급 적용하지 않는다.
- 사용자가 다른 언어를 명시하면 그 요구를 우선한다. 필수 기능이나 대상 환경 때문에 핵심 로직의 주 개발 언어를 Rust 대신 다른 언어로 바꿔야 하면 이유와 대안을 설명하고 사용자와 결정한다. 명시된 요구나 합의 없이 주 개발 언어를 임의로 대체하지 않는다.
- UI·설치기 제작 도구와 패키징·빌드 및 보조 스크립트·외부 라이브러리와 의존성의 언어 선택은 위 언어 변경 합의 대상에서 제외한다. 승인된 작업 범위에서 적합한 도구를 선택하며 Rust로 재작성하거나 언어가 다르다는 이유만으로 재승인을 요구하지 않는다. 다만 핵심 로직을 다른 언어로 옮기고 보조 도구로 명명해 이 기준을 우회하지 않는다.
- 설치 후 자동 업데이트와 OS 시작 시 자동 실행은 별도 기능이다. 요청 없이 추가하지 않는다.
- 신규 앱 또는 설치 기능 작업에서는 [설치 및 검증](references/installation.md)을 읽는다. 단순 코드 수정에는 이 문서를 일괄 적용하지 않는다.
- 데스크톱 앱의 새 화면을 디자인하거나 UI 변경을 요청받으면 [화면 디자인](references/design.md)을 읽는다. 신규 앱에는 실행 시작을 즉시 알리는 표시를 갖춘다. 자체 설치 UI를 제공하는 경우 승인된 설치 디자인을 적용하며, macOS의 표준 설치 흐름을 대체하려고 별도 설치기를 만들지 않는다. 배경 소재는 앱의 핵심 기능에 맞추고 텍스트는 실제 폰트로 구현한다. 기존 앱의 기능 수정만으로 디자인을 개편하지 않는다.
- 신규 데스크톱 앱·설치기 또는 표시 오류 수정에서는 [화면 디자인의 해상도·배율 기준](references/design.md)을 따른다. 4K와 OS 배율을 함께 고려하고 실제 작업 영역, 종횡비, 글자·버튼 접근성 및 모니터 간 배율 변경을 검증한다.

## Windows 기준

- 신규 Windows 설치형 앱은 바탕화면 바로가기, 작업표시줄 표시·사용자 고정 가능 여부, 실행 중 트레이의 창 열기·완전 종료, Windows의 정상 제거 기능을 갖춘다. 자동 고정은 하지 않는다.
- 기본 배포는 경량 온라인 설치기, 설치기가 내려받는 최신 정식 본체, 설치 없이 실행하는 포터블 ZIP의 세 구성이다. 명시된 오프라인 설치 등 다른 요구가 우선한다.
- 기존 앱 일부 수정에 이 구성을 소급 추가하지 않는다. 상세 구현·검증은 설치 및 배포 참고자료를 따른다.

## macOS 기준

- 앱 번들을 중심으로 해당 앱에 적합한 표준 설치·실행·제거 방식을 사용한다. 일반 앱의 Dock 표시와 종료 동작을 따르며 바탕화면 바로가기, Windows 작업표시줄·제거 등록, 트레이 또는 메뉴 막대 상주를 일괄 강제하지 않는다.
- 배포는 DMG 또는 앱 번들 ZIP 등 필요한 형식을 선택한다. 시스템 구성요소 설치 등 필요가 있을 때만 PKG나 별도 설치기를 사용한다. Windows의 경량 설치기·본체·포터블 3종을 강제하지 않는다.
- 지원 macOS 버전과 Apple Silicon·Intel 범위를 명시한다. 서명·공증·실행 허용 상태를 배포 경로에 맞춰 확인하고 보안 기능 해제를 정상 설치 방법으로 안내하지 않는다. 실제 Mac에서 확인하지 못한 항목은 미검증으로 보고한다.

## 배포 및 보호

- GitHub 소개·README 작성이나 배포·릴리스 요청이 있으면 [배포](references/deployment.md)를 읽고 관련 항목만 적용한다. README 작업만으로 공개·릴리스하지 않는다. 배포 대상의 기본값과 실제 공개 권한을 구분한다.
- 대상 프로젝트의 GitHub 첫 페이지를 새로 만들거나 개편할 때는 프로젝트별 커버, 짧은 소개, 눈에 띄는 다운로드, 주요 기능과 화면 예시로 정돈한다. 스킬·플러그인에도 README 시각 디자인 기준을 동일하게 적용하며 항목 순서만 맞추거나 텍스트만 나열해 완료하지 않는다. 커버와 설명은 해당 프로젝트의 특징에 맞게 새로 구성하며, 상세 기준과 고정 README 템플릿은 배포 문서의 ‘사용자용 첫 화면’을 따른다. 형식과 순서는 고정하고 프로젝트별 내용·시각 소재만 바꾼다.
- 공통 파일명·보안·도구 규칙은 현재 적용되는 사용자 지침을 따른다. 비밀키를 클라이언트·설치기에 포함하지 않고 사용자 데이터와 기존 설치본을 보존한다.
- 설치기 자체의 다운로드 통신은 앱 기능이다. AI의 GitHub 플러그인·브라우저 사용 규칙을 앱 내부 통신에 강제하지 않는다.

## 완료 보고

결과물 경로 또는 배포 링크, 실제 검증 결과, 남은 미검증·차단 항목을 간결하게 보고한다. 빌드 성공만으로 설치·배포 완료라고 하지 않는다. 작업과 무관한 전체 재검증이나 실제 운영 환경 변경을 하지 않는다.
